# 版本与兼容

<p class="lead">升级 Sani 时，你的短链接、脚本和部署配置能不能照常工作？这一页说明哪些东西受版本号约束、会怎样变化，以及 1.0 之前和之后的区别。</p>

## 版本号 {#semver}

Sani 遵循[语义化版本](https://semver.org/lang/zh-CN/)，版本号形如 `主版本.次版本.修订版本`：

- **修订版本**（比如 0.1.0 → 0.1.1）只修复问题，可以放心升级；
- **次版本**（比如 1.1 → 1.2）增加功能，不破坏已有的用法；
- **主版本**（比如 1.x → 2.0）才会有不兼容的修改，[更新日志](./changelog)会写明怎样升级。

**1.0 之前**，次版本也可能包含不兼容的修改，比如 0.1 → 0.2。每一处这样的修改都会在更新日志的“不兼容的修改”下列出，并附上升级方法。1.0 发布后，下面的承诺在整个主版本内有效。

## 承诺不变的部分 {#stable}

### 短链接

已有的短链接在升级后照常跳转：同样的地址、同样的状态码、同样的目标。保留的路径（`admin`、`api` 等，见[日常使用](../guide/usage)）只会在主版本变化时增加，所以不会有哪个已经在用的短码突然失效。

### HTTP API

[HTTP API](../reference/api) 里写明的接口、字段、取值和[错误码](../reference/api#errors)保持不变。一个次版本可能会：

- 增加新的接口；
- 在响应里增加新的字段；
- 在请求里增加可选的字段，不传时行为和以前一样；
- 增加新的错误码。

所以写脚本时，请忽略不认识的字段，并把不认识的错误码当作一般错误处理。错误里的 `message` 是写给人看的英文说明，可能随时调整，程序应当只看 `code`。

### 配置项

每一个 `SANI_*` [环境变量](../reference/configuration)保持名字、默认值和含义。新增的配置项，默认值会让 Sani 的行为和以前一样。

### 命令行

[子命令](../reference/cli)和它们的参数保持不变。

### 数据

- **数据库**：新版本能打开同一主版本内任何旧版本的数据库，并在启动时自动升级它的结构。反过来不行：旧版本打不开升级过的数据库，所以升级前请先[备份](../guide/operations#backup)，回退时用备份。
- **备份**：`sani backup` 得到的是一个普通的 SQLite 文件，可以直接用来恢复。
- **导出文件**：任何版本导出的 JSON 或 CSV，之后的版本都能导入。JSON 导出里的 `"version": 1` 表示文件格式的版本，格式有不兼容的变化时才会改变。

### 发布的文件

镜像名 `ghcr.io/dejavumoe/sani`、镜像标签的规则，以及二进制压缩包的文件名（见[部署](../guide/deploy#binaries)）保持不变，所以固定写在脚本里的下载地址不会失效。

## 不在承诺之内的部分 {#unstable}

- **管理界面**：布局、文案和快捷键可能随时改进。
- **日志**：日志是写给人看的，措辞和字段可能调整。唯一的例外是首次设置用的 `setup_code` 字段，文档里的命令依赖它。
- **数据库的内部结构**：表和列可能在任何版本里变化。请通过 API、导出或 `sani backup` 使用数据，不要直接读写数据库文件。
- **性能数据**：文档里的压测结果描述的是某一次测量，不是承诺。
- **Go 代码**：`internal/` 下的包不对外提供。

## 弃用 {#deprecation}

要去掉的东西，会先在更新日志和文档里标为“已弃用”，并在这个主版本余下的时间里继续工作，直到下一个主版本才真正移除。
